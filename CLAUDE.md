# CLAUDE.md

Правила для Claude Code в этом репозитории. Файл сложился из постановки задачи в начале работы и дополнялся по ходу, когда находились ошибки: каждая из них описана в [docs/ai-notes.md](docs/ai-notes.md), а правило, которое её предотвращает, записано ниже.

## Задача

Риск-сводка по синтетическому кредитному портфелю: два месячных среза (01.09.2026 и 01.10.2026), курсы к тенге по дням. Нужны схема `raw` с загрузкой CSV, вьюхи `reporting` (очищенная витрина и метрики на обе даты с изменением к 01.09), YAML-семантика, дашборд на Vega-Lite, README с итогами и тремя выводами для риск-комитета. Определения метрик — в README, раздел «Как я понимаю определения»; там же решения по неоднозначностям. Источник истины по определениям — страница задания, а не память модели.

## Стек и окружение

- PostgreSQL: сборка обязана работать на `postgres:16`. Локально кластер 17-й версии, поэтому синтаксис только тот, что есть в 16: `HEADER MATCH` (с 15), `pg_input_is_valid` (с 16). Не использовать то, что появилось в 17 (`MERGE ... RETURNING`, `JSON_TABLE` и т.п.), и не полагаться на память о параметрах сервера: `lc_collate` как параметра в 16+ нет.
- Локальный кластер — только через `scripts/pg_local.sh` (`./.pgdata`, порт 54329). На macOS postmaster стартует только с `LC_ALL=C`.
- Подключение — переменные `PG*` из `scripts/env.sh`; `psql` всегда с `-X -v ON_ERROR_STOP=1`.
- Python 3 с `pandas` и `pyyaml` (venv). Node и Playwright — только для скриншота.
- Внешних сервисов, секретов и чужих данных в репозитории нет и быть не должно.

## Слои

- `raw` — данные как в файле: все поля текстом плюс номер строки файла. Никаких преобразований.
- `reporting` — только вьюхи и функции. Типы, очистка, курсы, флаги — здесь.
- Правила — одно место: функции в `sql/30_reporting_rules.sql` (пороги PAR30/PAR90, корзина просрочки, NPL, ставка провизий, класс риска). Витрина, факты для выводов и проверки вызывают их, второй копии правил в SQL нет; сценарии «если бы кредит ушёл в 90+» берут ставку из `provision_rate(91, ...)`. Исключение намеренное: в `90_checks.sql` провизии и пороги PAR записаны ещё раз отдельно, чтобы сверить с ними функции.
- Метрики считаются только из `reporting.v_portfolio` (без списанных). `v_loans` со списанными — для аудита и сверки.

## Правила SQL

- Идемпотентность: `CREATE SCHEMA/TABLE IF NOT EXISTS`, `CREATE OR REPLACE VIEW/FUNCTION`, загрузка через `TRUNCATE ... RESTART IDENTITY` и `\copy` в одной транзакции.
- `CREATE OR REPLACE VIEW` не удаляет и не переименовывает колонки: новые колонки добавлять только в конец списка; переименование — отдельной миграцией с `DROP VIEW`.
- `numeric` без промежуточного округления. Округление — только в подписях (`reporting.fmt_*`).
- Курс строго на дату среза. Нет курса — сумма `NULL`, и проверка останавливает сборку. Никаких `coalesce` и «последнего доступного курса».
- Полные дубли схлопываются; разные версии одного кредита на дату — ошибка сборки, а не выбор «любой».
- PostgreSQL не гарантирует порядок вычисления условий в `WHERE`: приведение типа после regex-проверки писать через `CASE`, а не `AND`/`OR`.
- Проверка сырья не должна зависеть от типизированных вьюх: битое значение уронит вьюху раньше, чем проверка скажет, в чём дело.
- Источник фактов для `CROSS JOIN` — агрегат без `GROUP BY` (ровно одна строка). Пустой CTE в соединении молча обнуляет весь результат.
- `\if` в psql принимает только boolean.
- Не опираться на текст сообщений сервера (WARNING, ERROR): он переводится по `lc_messages`. В тестах — своя метка в выводе или код SQLSTATE.
- Сортировка выгрузок по тексту — с `COLLATE "C"`, иначе порядок строк зависит от локали базы.

## Расчёты для выводов

- «Вклад в долю» считать как разницу долей с ним и без него: меняется и числитель, и знаменатель. Доля его суммы в портфеле — другое число.
- Довод из данных проверять на контрольной группе: показатель должен различать группы, иначе он ничего не доказывает (так отпал довод «излечения без погашений» по динамике остатка).
- База для вывода — без того, что уже учтено в метрике: «скрытая реструктуризация» считается только по кредитам без отметки о реструктуризации.
- Утверждение словами («ни одного», «четыре») проверять запросом так же, как число.

## Проверки — обязательны после любой правки

```bash
make build check test screenshot
```

- `sql/90_checks.sql` запускается внутри `scripts/build.sh` до выгрузки, падает громко и печатает все проверки; граничные случаи (ровно 30 и 90 дней, реструктуризация с малой просрочкой) проверяются на функциях правил и на реальных граничных строках, а проверка сначала убеждается, что такие строки есть.
- `checks/verify_independent.py` — второй расчёт из CSV, написан без доступа к SQL. Правка SQL, после которой он расходится, — ошибка, пока не доказано обратное. Его не подгонять под SQL.
- Новый контроль сначала проверить на заведомо плохом входе (`scripts/test_controls.sh`) и на заведомо хорошем: сравнение значения с самим собой обязано давать «совпало», а счётчик объектов не может быть нулём.
- Числа в README — только из выгрузок SQL: `v_committee_facts`, `v_risk_metrics_long`, `v_data_quality`, `v_portfolio_bridge`. Таблица итогов рендерится `checks/check_readme_numbers.py --write`; число руками в текст выводов не вписывается, сначала факт во вьюхе и в независимом пересчёте.
- Дашборд проверяется по скриншоту, а не по коду спеки: дубли подписей, наезды и обрезки видны только на картинке. `scripts/screenshot.mjs` падает на любой ошибке или предупреждении в консоли.

## Где ИИ нельзя верить без проверки

- Определения на границах (30/90 дней, приоритет NPL над корзинами просрочки) — только через тесты.
- Итоговые числа — только после независимого пересчёта.
- «Проверка прошла» — только если доказано, что она умеет падать.
- Версии PostgreSQL и поведение psql — по документации, не по памяти.
- Вёрстка графика — по скриншоту.
